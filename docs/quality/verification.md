# Проверка и приёмка

## Что проверяет текущий каркас

```sh
python3 scripts/check_sdd.py
python3 -m unittest discover -s tests -v
python3 scripts/extract_source.py --check
```

Первая команда проверяет обязательные файлы, JSON, уникальность и ссылки ID, локальные Markdown-ссылки, комплект спецификаций, структурную трассировку и SHA-256 PDF. Она также проверяет текущую рабочую задачу, аппрув её редакции, критерии самопроверки и архив. Вторая запускает воспроизводимые позитивные и негативные тесты валидатора на временных копиях. Третья повторно извлекает три страницы и сравнивает сохранённый текст; для неё нужен `pdftotext`.

Это проверки документации. Они не запускают приложение, не анализируют внешние ссылки, не доказывают клиническую правильность и не удостоверяют соответствие законодательству. При добавлении кода список команд расширяется в плане функции.

Фактический результат подготовки каркаса — в [отчёте от 2026-10-18](reports/2026-10-18-foundation.md).

## Проверка процесса задач

До выполнения задача записывается в [CURRENT_TASK.md](../../CURRENT_TASK.md) и проходит ревью и аппрув разработчика. Проверка существующего состояния допустима до аппрува; изменение реализации выполняется после него. Валидатор требует совпадение согласованной редакции, заполненные сведения об аппруве и критерии `CHECK-NN`. Он проверяет форму записи; личность согласующего и фактическое содержание его решения не удостоверяет.

После выполнения агент самостоятельно проверяет каждый критерий, записывает команду/действия, реальный результат и свидетельства в `checks`. Для завершения обязательны успешные критерии, дата, обновление `PROJECT_STATUS.md` и результат проверки `TECH_DEBT.md` в `completion`. Возникающий долг фиксируется сразу. При отсутствии нового долга это указывается явно.

В архив допускаются только `completed`-задачи; корневой файл после переноса становится `idle`. Непройденная проверка не переносится в архив под видом готовой задачи. Завершение рабочей задачи не закрывает автоматически всю связанную спецификацию.

Проверки переходов, неверной редакции аппрува, пропущенных критериев, долга и архива находятся в [tests/test_check_sdd.py](../../tests/test_check_sdd.py). Результаты внедрения процесса — в [отчёте WORK-0001](reports/2026-10-18-work-0001.md).

## Метрики

PDF задаёт 13 технических направлений в NFR-001–NFR-013, но не задаёт численных порогов. Они сохранены в реестре: быстродействие, качество извлечения, надёжность, эргономика, обоснованность, нагрузка, восстановление, кроссплатформенность, масштабируемость, расширяемость правил, гибкость и полнота данных, защищённость.

Для текущей задачи выбирайте применимые показатели. Когда требуется численная цель, сначала согласуйте её и метод измерения в задаче; не придумывайте время отклика, доставки, допустимую потерю или нагрузку. Фиксируйте среду, объём данных и фактический результат. Q-010 остаётся открытым до такой задачи.

Измерение доставки алерта не равно времени реакции врача. Если канал не подтверждает доставку, граница измерения указывается явно. Наличие метрики не требует заранее вводить отдельный сервис или пользовательскую функцию.

## Свидетельства

Для каждого выполненного сценария сохраните: ID `TEST`, дату, версию кода, среду, команду/шаги, результат, фактический вывод и ссылку на артефакт без медицинских данных. В `traceability.json` отметка `passed` требует непустого `evidence`; в приёмочном документе даётся проверяемый протокол. Ссылка сама по себе не подтверждает качество свидетельства.

Статус `verified` у требования возможен только при полном покрытии и фактических проверках всех его частей. Отчёт о создании документации не заменяет отчёт о реализации.

## Проверенный серверный срез WORK-0008

Фактические команды и среда — [отчёт](reports/2026-10-21-work-0008.md). Сервер проверяется на PostgreSQL, браузер — отдельно от прямого API. Основная команда:

```sh
docker compose --profile dev run --rm app python manage.py test accounts care reports audit -v 2
```

32 теста покрывают аккаунты, CSRF, роли/связи, вложенные чужие объекты, транзакции, конкуренцию и аудит. Сценарии tests/browser/run.py и accessibility.py проверяют независимые сессии, почту, интерфейс и очистку состояния. tests/docker/containers.py и reset_limits.py проверяют сохранность, восстановление, отказ БД, два Gunicorn worker и рестарт. Эти операционные сценарии разрешены только в выделенном синтетическом проекте; порядок запуска — в README. Старые отчёты UI не заменяют проверку сервера.
