## Исторический пользовательский интерфейс WORK-0004

Согласованная редакция 1: переработать существующий `index.html` в сам кабинет. Desktop: боковая навигация и рабочая область; mobile: компактная шапка и навигация. Использовать обычную прокрутку страницы без вложенного телефона, презентационной колонки, выбора роли и панели имитаций. Формы компонентов сохраняются из референса; цвета уточнены WORK-0005.

WORK-0005, редакция 1: заменить только цветовые значения и соответствующие CSS-имена растительной зелёной палитрой: `#F7FAF3` — фон, `#EEF4E7` — боковая панель, `#243A25` — текст, `#60705E` — второстепенный текст, `#386641` — основные акценты, `#2B5133` — hover, `#E6EEDC`/`#D7E5C7` — мягкие поверхности, `#476D32` — фокус. Красная семантика ошибки сохраняется. Контраст обычного текста и включённых кнопок проверяется с целью не менее 4,5:1. HTML, JavaScript и компоновка не меняются; прежний полный функциональный прогон не объявляется повторно выполненным.

Адреса: пустой hash и `#/patient` открывают главную пациента; `#/patient/report` — форму; `#/patient/history` — историю; `#/doctor` — список; `#/doctor/patients/patient-a` и `patient-b` — вымышленные карточки. Нераспознанный адрес не подставляет произвольного пациента. Hash содержит только имя раздела/синтетический ID, без текста записи. Это навигация локального интерфейса, не серверная роль. Вход и выбор стека не реализуются.

Сохранить минимальное состояние в памяти вкладки: исходные вымышленные профили и записи, черновик, валидация, статус добавления. Удалить `mode`, `failNext`, выбор искусственных состояний и соответствующие обработчики. Локальную операцию обрабатывать с блокировкой повторной отправки и сохранением черновика при ошибке. Значения выводятся безопасно как текст; данные не пишутся в URL, логи, постоянное хранилище или сеть.

Одна компактная отметка тестовой среды и вымышленных данных вместо пояснений на каждой карточке. У формы — значимая пользователю информация о хранении до перезагрузки. Остальные технические ограничения описаны в README. Проверки ошибок выполняются средствами браузерного прогона без новых управляющих элементов для посетителя.

AC-001-15–AC-001-18 проверяются Firefox 1440/768/390 px, пользовательскими переходами и негативным вводом; фактический отчёт — WORK-0004. Стек, авторизация и хранение приложения остаются открытыми. Весь согласованный объём ограничен интерфейсом.

## Исходный серверный план (уточнён WORK-0008 ниже)

Основания первого среза — CON-001, CON-002, FR-005 и требования конфиденциальности. Реализовать только необходимое сейчас самым простым достаточным способом, без дополнительных сервисов и будущих функций. Каждый пункт ниже нужен для действующих критериев среза.

2. Определить серверную сессию, закрытый демонстрационный вход и способ установки ролей. Нельзя принимать роль из localStorage как основание доступа. Для cookie-сессии предусмотреть защиту изменяющих запросов от CSRF и безопасные параметры cookie с учётом среды.
3. Уточнить модель и миграции: User, DoctorProfile, PatientProfile, CareRelationship, SelfReport, AuditEvent и хранимая идемпотентность.
4. Реализовать модуль серверной авторизации и контракты, затем интерфейс. Сначала проходится прямой серверный сценарий доступа, затем та же операция через UI.

## Исходные предварительные контракты

Названия маршрутов — предложение для согласования с фреймворком, не готовый API:

| Метод и маршрут | Пользователь | Поведение |
| --- | --- | --- |
| `GET /api/me` | Аутентифицированный | Серверные ID и роль без медицинских сведений |
| `GET /api/patients` | Врач | Только действующие связанные пациенты, минимальные данные |
| `GET /api/patients/{id}/self-reports` | Ведущий врач | Серверная проверка текущей связи при каждом чтении |
| `GET /api/me/self-reports` | Пациент | Только собственная история, стабильная сортировка и ограниченная выборка |
| `POST /api/me/self-reports` | Пациент | Валидация, ключ идемпотентности, транзакционное сохранение и аудит |

В запросе создания: `observed_at`, `text`; ключ повторного запроса передаётся согласованным заголовком. `patient_id`, `doctor_id`, `role`, серверное время и автор не являются редактируемыми полями. Лишние поля не изменяют права и не позволяют записать чужого пациента.

Ошибки: отсутствие сессии; отказ по роли/связи без утечки существования; ошибка валидации с кодами полей; конфликт ключа; временная серверная ошибка с безопасным сообщением. Конкретные HTTP-коды и формат ошибки фиксируются до реализации. Ответы с медицинскими данными не кэшируются публично; клиентский кэш очищается при выходе и смене пользователя.

## Сохранность и конкуренция

- Ограничение уникальности по пользователю и ключу повторного запроса действует в хранилище, а не только в UI.
- Совпадение ключа и содержимого возвращает существующий результат, несовпадение — конфликт. Проверка и запись атомарны; есть тест параллельного повтора.
- Запись самоотчёта и аудит создания согласованы транзакцией. Сбой не должен выдавать успех без записи.
- Проверка текущей связи выполняется при запросе, а не копируется в долгоживущую сессию как неизменяемое право.
- Текст не пишется в обычные логи. В аудит включаются ссылки на объекты без копирования свободного текста.

## Интерфейс

Пациент: форма, подтверждение записи, история и пустое состояние. Врач: список своих пациентов и история выбранного пациента. Явные состояния загрузки, отказа, ошибки и повтора; подписи полей и ошибок доступны с клавиатуры. Показать обозначение синтетического демо и отсутствие клинической интерпретации.

## WORK-0008 — обязательный контракт реализации

По аппруву редакции 1: решение ADR-0002. User с email без регистра и уникальным ограничением БД, display_name, role (patient/doctor), doctor_approved. Публичный ввод не меняет staff/superuser/допуск/связь. CareRelationship имеет не более одного активного врача для пациента. SelfReport хранит patient, observed_at, text (trim, 1–2000), created_at, idempotency_key; уникальность patient/key. AuditEvent хранит субъект/действие/объект/исход без медицинского текста и секретов.

Аккаунты: /_allauth/browser/v1/… — готовые session/signup/login/email verify/password request/reset/change операции; только browser. Схема allauth сохраняется. POST требует CSRF; HTML устанавливает CSRF-cookie. /api/me возвращает id/name/role/doctor_approved и ведущего врача; все прикладные маршруты требуют активную сессию и подтверждённый email. Ожидающий врач видит только свой статус.

Прикладные пути без завершающего slash: GET /api/patients, GET /api/patients/{id}/self-reports и /{report_id} — допущенный ведущий врач. GET/POST /api/me/self-reports — пациент. POST принимает только observed_at/text и Idempotency-Key. GET истории: cursor, limit (1–100, по умолчанию 30), порядок observed_at DESC, id DESC. Ответ {results, next_cursor}; курсор подписан, привязан к пациенту. По умолчанию безопасный лимит, полный интерфейс поддерживает загрузку следующих страниц.

Ошибки прикладного API: 401 без действующей сессии; 403 роль/допуск/CSRF; 404 чужой или отсутствующий объект без различимого содержимого; 400 неверные поля/курсор; 409 несовпадение тела при повторном ключе; 503 недоступность БД/SMTP. Формат {error: {code, message, fields?}}. Данные и ошибки закрытых API: Cache-Control no-store. Allauth использует свой документированный формат с клиентским переводом ошибок.

Создание самоотчёта и аудит создания — одна транзакция; повтор проверяется по сохранённым значениям, уникальность БД разрешает гонку. Чтение/отказ аудируются отдельно. Отзыв связи/допуска проверяется на каждом запросе, без сохранения прав в сессии. Операторские команды doctor_access (approve/revoke), care_relationship (assign/revoke), seed_demo (opt-in dev). Операционные права определяются доступом к контейнеру, субъект аудита — service:operator, без приписывания личности.

Сборка: docker compose --profile dev build app. Миграции и cache-table подготавливает entrypoint до Gunicorn. GET /health/ready проверяет БД. Тесты: docker compose --profile dev run --rm app python manage.py test accounts care reports audit -v 2. Браузерный прогон хранится в tests/browser; отдельный Compose-проект для разрушительных проверок. Синтетические секреты передаются окружением, наружу письма не отправляются.

Результат WORK-0008: модели, миграции, контракты и команды реализованы; отдельные DoctorProfile/PatientProfile не созданы, потому что все текущие поля находятся в User. Frontend обслуживается Django/WhiteNoise из frontend/templates и frontend/static; прямое открытие HTML-шаблона больше не является запуском сайта. Проверки и ограничения — [отчёт WORK-0008](../../docs/quality/reports/2026-10-21-work-0008.md).
