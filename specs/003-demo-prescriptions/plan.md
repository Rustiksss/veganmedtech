# План SPEC-003

Используются выбранные Django/DRF/PostgreSQL и существующая сессия/CSRF, без новых зависимостей. Приложение prescriptions отделяет версионированный каталог названий от UI. Новая таблица DemoPrescription хранит UUID подтверждения unique, FK пациента/врача PROTECT, снимок названия/ID и версии, комментарий, confirmed_at и synthetic=true. Миграция только добавляет таблицу; прежние данные не изменяет.

Контракты: GET /api/prescriptions/catalog — допущенный врач; POST /api/patients/{id}/prescriptions/preview принимает drug_id/note, подписывает предложение с пациентом/врачом/версией/UUID; срок 30 минут. POST /api/patients/{id}/prescriptions принимает только proposal_token и confirmed=true (именно boolean). Подпись Django связывает неизменный текст с конкретным пациентом/врачом и версией; это необходимо для подтверждения точного предложения без отдельной таблицы черновиков. Подтверждение блокирует строку пациента, как существующая операция смены связи, повторно проверяет связь и создаёт запись + аудит одной транзакцией. UUID защищает от повторного запроса после сетевого сбоя. GET этой коллекции — активный ведущий врач; GET /api/me/prescriptions — только сам пациент. Новые записи первыми; в ответе нет email/токенов. Ошибки используют существующий безопасный обработчик. Токен только в памяти вкладки; никогда в URL/хранилище/логах.

Frontend: новая навигация пациента и форма в карточке врача. При изменении ввода предложение сбрасывается; подтверждение повторяет тот же токен при неопределённом сбое. Маркер маршрута исключает запись позднего ответа на другой экран; смена аккаунта очищает состояние. Комментарии выводятся с HTML escaping. Обычные журналы не содержат комментарий; аудит хранит IDs и тип действия.

Проверки: Django на отдельной PostgreSQL (включая прямые негативные запросы, конкурентный повтор и транзакционный отказ); настоящий Firefox, клавиатура и 390/1440; node --check, check_sdd.py, unittest. Только вымышленные аккаунты. Без публикации и обращения к рабочей БД.
