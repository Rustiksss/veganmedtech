# VeganMedTech · Клинический компас

Репозиторий: [Rustiksss/veganmedtech](https://github.com/Rustiksss/veganmedtech), основная ветка `main`.

Веб-приложение и основа SDD для поддержки решений врача. Язык интерфейса и документации — русский. Первый серверный срез реализован в WORK-0008; фактический статус находится в [PROJECT_STATUS.md](PROJECT_STATUS.md), план/аппрув — в [WORK-0008](tasks/completed/WORK-0008.md), проверки — в [отчёте](docs/quality/reports/2026-10-21-work-0008.md).

Серверный объём: аккаунты, подтверждение почты, вход/выход и пароли, допуск врача, связь с пациентом, сохранение/история самоотчётов и аудит. Врач видит записи только связанных пациентов. Используются исключительно вымышленные данные. Клинический движок, назначения, алерты и промышленное размещение не реализованы.

## Локальный запуск

Нужны Docker Engine и Docker Compose. Создайте новые секреты для своего локального окружения и сохраните их в приватной конфигурации. Приложение само не читает `.env`-файлы; Compose может использовать ваш файл через `--env-file`. Новый `.env.example` — только шаблон, действующих секретов в нём нет. Существующие приватные файлы агент не читает.

Пример первого запуска с переменными текущей оболочки:

```sh
export DJANGO_SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(64))')"
export POSTGRES_PASSWORD="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
export APP_DEV_MODE=1
export APP_BASE_URL=http://localhost:8000
docker compose --profile dev up --build -d --wait
```

Сайт: `http://localhost:8000`. Письма тестовой среды: `http://localhost:8025` (Mailpit). Они не отправляются наружу. База и SMTP доступны только во внутренней сети Compose, опубликованные HTTP-порты привязаны к loopback. Нельзя использовать этот режим для размещения в интернете.

Для следующего запуска используйте **те же** POSTGRES_PASSWORD и DJANGO_SECRET_KEY: сохранённый том содержит БД с исходным паролем, смена ключа инвалидирует сессии/подписанные ссылки. Не генерируйте их повторно поверх существующего окружения. Передавайте SMTP/домены/allowed hosts явно при изменении конфигурации; доверие произвольным proxy-заголовкам выключено.

На старте применяются миграции и создаётся таблица cache ограничений; автоматически аккаунты и ведущий врач не создаются. Сборка не подключается к БД и не использует настоящие секреты. Runtime работает с UID 10001. Статус готовности: `GET /health/ready`, при недоступности БД — 503.

```sh
docker compose ps
docker compose stop
docker compose --profile dev up -d --wait
```

Остановка и пересоздание контейнеров сохраняют named volume. Не удаляйте томы для обычного перезапуска.

## Доступ с других устройств через интернет

WORK-0014/WORK-0015: пилот доступен по **https://94.103.3.149** с других устройств без SSH-туннеля и общего пароля браузера. Вход — через обычную форму аккаунта приложения. Допустимы только вымышленные имя, почта и сведения; медицинский и production-допуск отсутствуют.

Регистрацию и восстановление пароля подтверждает организатор через защищённый Mailpit по адресу **https://94.103.3.149:8443/**. Письмо в настоящий почтовый ящик не поступает. Врач дополнительно ожидает операторского допуска, связь с пациентом назначает оператор. Полный модуль четырёх учебных опросников выдаётся только действующему пациенту с подтверждённым адресом через `/api/questionnaires/module` с `Cache-Control: no-store`; исходного, хешированного и сжатого модуля в публичной статике нет. Ответы остаются в памяти вкладки и очищаются при выходе.

Обновление опубликованного пилота:

```sh
bash scripts/deploy.sh --internet
```

Скрипт сохраняет секреты, том БД и TLS-хранилище, проверяет dump перед обновлением и сохраняет приватные копии серверной/proxy-конфигурации. Перед снятием Basic Auth обязательно проверяет закрытую доставку модуля и отсутствие публичных копий. Неизменный образ повторно использует только после проверки content ID/метки/архитектуры. Повторный запуск не возвращает общий пароль. Прежний приватный `demo-access.json` сохранён для отката, новая поставка его не использует.

Caddy 2.11.7 установлен проверенным бинарным файлом на хосте, работает пользователем `veganmedtech-proxy` через systemd. Let's Encrypt выдаёт IP-сертификат профиля `shortlived`; продление автоматическое, TLS-данные постоянны в `/var/lib/veganmedtech-caddy/production`. Публичны HTTP 80 (ACME/перенаправление), HTTPS 443 приложения и HTTPS 8443 операторского Mailpit; SSH сохраняется. Приложение 18008 и Mailpit 18025 остаются на loopback, PostgreSQL и административный API Caddy наружу не публикуются.

Оператор открывает **https://94.103.3.149:8443/** на компьютере или телефоне. Логин — `operator`, отдельный пароль создаётся на сервере один раз и сохраняется при повторном деплое. Реквизиты можно один раз получить в своём SSH-терминале:

```sh
ssh veganmedtech-server cat /opt/veganmedtech/config/mailpit-access.json
```

Используйте поле `password`; `password_hash` служит Caddy. Не копируйте реквизиты в репозиторий, отчёты и общий чат. Это **общий ящик организатора**: пароль открывает письма всех участников, включая ссылки подтверждения и сброса. Пациентские/врачебные аккаунты приложения не дают доступа к Mailpit. Письма на настоящую почту не доставляются; ссылки в них ведут на основной HTTPS-origin :443.

UI, assets, API и WebSocket защищены одним паролем. Прямой Mailpit :18025 остаётся на loopback; отдельный proxy :8443 сохраняет Host с портом для Origin и удаляет Cookie/Authorization перед upstream. Основной сайт :443 использует обычный вход приложения. Сеть устройства должна разрешать HTTPS на 8443; физический телефон отдельно не проверялся, проверены Firefox и ширины 1440/390 px.

Альтернативный доступ через SSH-туннель сохраняется:

```sh
ssh -N -L 18025:127.0.0.1:18025 veganmedtech-server
```

В этом случае откройте `http://localhost:18025`. Команды допуска врача и назначения связи описаны ниже. Браузерные проверки создают собственные вымышленные аккаунты: после проверки они отключаются, связи отзываются, самоотчёты удаляются. События аудита и их авторы сохраняются.

```sh
python3 tests/browser/run.py --mailpit-check --bidi-port 19258
python3 tests/browser/run.py --internet-check --bidi-port 19258
```

Команда предназначена только для указанного пилота и требует заранее запущенного отдельного Firefox BiDi и настроенного SSH. Проверка сертификатов включена. Протокол — [WORK-0015](tasks/completed/WORK-0015.md), история основного пилота — [WORK-0014](tasks/completed/WORK-0014.md). Проверены Firefox, 390/1440 px и внешний сетевой клиент; физический телефон отдельно не проверялся.

Диск остаётся 5 GB, резерв — не менее 256 MiB. Для первой поставки WORK-0014 после проверенного локального сохранения и загрузки копии адресно удалены только три согласованных неиспользуемых тега WORK-0012. Образ WORK-0013, исходники, конфигурации, dump и том сохранены. Автоматической очистки нет.

В WORK-0015, редакции 2, отдельно согласована и выполнена разовая очистка 67 файлов воспроизводимых APT-кэшей (289 689 600 байт) под штатными apt/dpkg-блокировками. Пакеты/настройки/образы/тома/копии сохранены; автоматика обновления не менялась. Рост кэшей может снова потребовать явного обслуживания небольшого диска. При недостатке резерва скрипт останавливается до обновления.

Для возврата к Mailpit только через SSH оператор может восстановить proxy-конфигурацию перед первой поставкой WORK-0015:

После этого проверьте главную :443 и закрытый :8443. Приложение/БД не требуют отката: их образ не менялся. Приватные реквизиты сохраняются; следующий `--internet` с текущей версией снова применит настройку доступа Mailpit.

Если полный транспорт и импорт одновременно не помещаются, скрипт допускает последовательные фазы через существующий tmpfs `/dev/shm` только при проверенных предпосылках: Docker 29.9.2/containerd, реальное наличие базовых raw blob, совпадение RootFS, хеши/размеры слоёв и достаточная свободная RAM/tmpfs. Проверенный архив временно копируется в закрытый RAM-каталог и удаляется с SSD до импорта; RAM-копия убирается после импорта/ошибки. Полный размер образа и резерв 256 MiB сохраняются в оценке, неизвестные предпосылки возвращают полную дисковую оценку или отказ. Другие старые артефакты автоматически не удаляются. Производственная ёмкость, внешний SMTP и реальные данные этим не подтверждаются.

Для возврата к WORK-0013 с общим паролем сохранены её образ/исходники и копии конфигурации перед первым пилотом. WORK-0014 миграций БД не добавляет. Оператор проверяет совместимость схемы; выполняет на сервере:

## Деплой на 94.103.3.149 по SSH

Исторический режим WORK-0012: `bash scripts/deploy.sh` разворачивает приложение как **закрытое демонстрационное окружение через SSH**. Для уже опубликованного пилота WORK-0014 используйте `--internet`, как описано выше. Сайт и Mailpit слушают только `127.0.0.1` сервера; доступ идёт через SSH-туннель. Используйте вымышленные сведения. Домен, публичный HTTPS и внешняя отправка писем этим скриптом не настраиваются.

Локально нужны Bash, Python 3, OpenSSH и работающий Docker с Buildx. Настройка подключения выполняется один раз. Сначала сверьте host fingerprint через консоль хостера командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`. Для этого сервера 2026-10-24 разработчик подтвердил ED25519 `SHA256:l/VOykTlQqPbpaEVLxQGvAORz9/KmKD1mB64+tZfyZs`. При изменении отпечатка остановитесь и выясните причину. Затем установите **публичный** ключ обычным `ssh-copy-id -i ~/.ssh/id_ed25519.pub root@94.103.3.149`; пароль вводится только в запрос SSH и не сохраняется в проекте. Закрытый ключ остаётся локально.

В пользовательском `~/.ssh/config` нужен блок (сохраните остальные настройки):

```sshconfig
Host veganmedtech-server
    HostName 94.103.3.149
    User root
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    StrictHostKeyChecking yes
    ForwardAgent no
```

Проверка и первый/повторный деплой из корня проекта:

```sh
ssh -o BatchMode=yes veganmedtech-server id -un
bash scripts/deploy.sh --dry-run
bash scripts/deploy.sh
```

Dry-run показывает список исходников и действия, не использует SSH и не собирает образ. Скрипт не зависит от Git: готовит контекст только из `backend`, шаблонов/статики frontend и необходимых файлов Docker/деплоя; собирает локально linux/amd64 образ и передаёт готовый образ вместе с этим кодом и manifest. Сервер не выполняет сборку. Dockerfile использует отдельные этапы: в runtime нет uv и его download-кэша, версии зависимостей/lock сохранены. Локальные `.env*`, ключи, служебные каталоги, виртуальная среда, кэши и исходные материалы исключены; ссылки и специальные файлы в разрешённых путях отклоняются. На сервер передаётся только код, не локальные секреты или БД.

На свежей поддерживаемой Debian/Ubuntu при отсутствии Docker скрипт устанавливает его из [официального репозитория](https://docs.docker.com/engine/install/ubuntu/). Существующий движок не переустанавливается, конфликтующие пакеты не удаляются; нужны работающие Docker и Compose с `up --wait-timeout`. Чужой каталог/проект/том/сеть или занятые посторонним процессом порты вызывают отказ. Параллельные деплои блокируются.

Перед передачей скрипт требует свободное место под полный размер готового образа, весь транспортный файл и резерв 256 MiB. Размеры измеряются локально для каждой версии. На сервере проверяются размер/контрольная сумма архива, tag/переносимый ID/архитектура/метка образа; ID — SHA-256 хешей слоёв и настроек запуска, одинаковый для classic store и containerd Docker 29; после Docker load удаляется только временный архив. Перед запуском и после HTTP-проверок должно оставаться не менее 256 MiB. Это технический резерв закрытого демо, а не расчёт ёмкости для эксплуатации. В WORK-0012 используется прежний диск сервера 5 GB; первая неудачная попытка с серверной сборкой сохранена в отчёте. Разовая адресная очистка её кэша и APT-индексов согласована отдельно, в обычный деплой она не включена. Автоматическая очистка образов, кэшей, копий и томов не выполняется.

Собственные файлы находятся в `/opt/veganmedtech`: `config/server.env` с правами `0600`, `releases/<ID>`, закрытые `backups/<ID>.dump`, ссылки `current` и `previous`. Проект Compose всегда `veganmedtech`, том — `veganmedtech_postgres_data`, образ каждой версии — `veganmedtech-server:<ID>`. Сервисы имеют `restart: unless-stopped`. Не удаляйте том при обновлении.

Первый запуск создаёт независимые случайные DJANGO_SECRET_KEY/POSTGRES_PASSWORD на сервере. Следующие запуски сохраняют их и проверяют конфигурацию без вывода значений. Неполный файл или конфигурация, не соответствующая закрытому демо, не заменяются автоматически. Compose запускается с очищенным окружением, явным env-файлом и двумя Compose-файлами. Внешние переменные оболочки не подменяют серверные секреты. Стандартные локальные команды Compose не затронуты.

Готовый образ собирается локально до отправки; сервер только загружает и запускает его. Если БД уже существует, она должна работать: скрипт сохраняет `pg_dump -Fc`, проверяет архив через `pg_restore --list` и только затем запускает контейнеры с ожиданием готовности. Успех требует readiness БД/приложения и HTTP-ответов сайта/почты. Миграции выполняет обычный entrypoint. Короткий перерыв при замене контейнера возможен; автоматический откат схемы не выполняется. При сбое сохраняются предыдущие исходники/образы и созданные копии; неудачная передача не запускается. Старые версии, образы и копии не удаляются автоматически: следите за местом и удаляйте только выбранные ненужные артефакты своего проекта.


## Аккаунты и доступ

1. Выберите пациента или врача, заполните вымышленные имя/email и уникальный пароль не короче 12 символов.
2. Найдите письмо в локальном Mailpit, откройте ссылку и нажмите подтверждение. Затем войдите.
3. Врач после подтверждения адреса ожидает допуска оператора. Одобрение не назначает ему пациентов автоматически.
4. Оператор с доступом к контейнеру отдельно одобряет врача и назначает связь:

```sh
docker compose exec app python manage.py doctor_access approve doctor@example.test
docker compose exec app python manage.py care_relationship assign patient@example.test doctor@example.test
```

Отзыв и смена связи:

```sh
docker compose exec app python manage.py doctor_access revoke doctor@example.test
docker compose exec app python manage.py care_relationship revoke patient@example.test
docker compose exec app python manage.py care_relationship assign patient@example.test other-doctor@example.test
```

Команды проверяют роли и подтверждение адреса, изменения аудируются как служебные операции. Личность человека не устанавливается по переданной строке. Публичного изменения роли, допуска и связи нет. Ожидающий врач видит только свой статус; отключение аккаунта, отзыв допуска или связи учитывается следующим запросом старой сессии.

Пациент сохраняет дату/время наблюдения и текст 1–2000 символов. После обновления запись остаётся в PostgreSQL и доступна ведущему врачу в независимой сессии. Один ключ повторной отправки создаёт одну запись; изменение тела с тем же ключом даёт 409. История имеет ограниченную выборку и загрузку следующих страниц. Самоотчёт не получает диагноза или клинических баллов.

Для восстановления пароля используйте «Забыли пароль?»; для смены — ссылку в кабинете. Выход и смена пароля инвалидируют прежние сессии. Пароли хранятся как Argon2id, сессия — в БД; клиент не сохраняет пароль или session token в browser storage. Для HTTPS-конфигурации cookie Secure включён, локальный HTTP требует APP_DEV_MODE=1.
