## Запрос и цель

Поручение разработчика 2026-10-24: сделать скрипт автоматического деплоя проекта на `94.103.3.149` и добавить подключение с одним из существующих SSH-ключей. В ответе на уточнение разработчик указал пользователя `root`. Переданный пароль предназначен только для первоначального SSH-входа; его значение в задаче, скриптах, аргументах команд и отчётах не сохраняется.

Уточнение разработчика после неудачного первого запуска: «а не возможно ли сделать так, чтобы оно запустилось на 5 гб?». Редакция 2 сохраняет текущий диск сервера; меняется место сборки и состав runtime-образа. Ни увеличение диска, ни подключение платных сервисов не требуются этой редакцией.

Результат: настроенное SSH-подключение `veganmedtech-server`, команда `bash scripts/deploy.sh` для первого и повторных развёртываний и фактически проверенная поставка текущего приложения на этом сервере. Основание — служебное поручение разработчика; новой продуктовой функции или условия PDF не вводится. Технические границы связаны с CON-010, NFR-007, NFR-013 и существующими AC-001-34/AC-001-37 в [SPEC-001](../../specs/001-access-and-self-report/spec.md). Полное выполнение этих требований одним деплоем не заявляется.

Домен и внешний SMTP не предоставлены. В этой редакции сайт и Mailpit доступны только через SSH-туннель к loopback-портам сервера. Это закрытая демонстрационная поставка на вымышленных данных. Публичный HTTP, настройка домена/HTTPS и отправка почты наружу в объём не входят; при запросе публичного сайта решение нужно уточнить до реализации.

## Границы и риски

Редакция 1 была одобрена и частично выполнена; её аппрув и исходный план сохранены ниже. Из-за существенного изменения способа сборки/передачи редакция 2 прошла отдельное согласование 2026-10-24. До полученного аппрува выполнялись только чтение, проверки существующего состояния и уточнение этого файла. На момент ревью редакции 2 оптимизация Dockerfile, новая логика деплоя и очистка серверного build-кэша ещё не выполнялись; итог реализации приведён в самопроверке ниже.

Входит: локальная сборка компактного образа с передачей готового результата на сервер вместо серверной сборки; разовое освобождение воспроизводимых файлов первой неудачной попытки по точно проверенным ID; установка одного публичного ключа в `root` на указанном сервере без удаления существующих ключей; добавление локального SSH-алиаса с сохранением пользовательского config; минимальный скрипт переноса и запуска текущей Docker-поставки; независимые серверные секреты; сохранение БД при повторном деплое; копия перед обновлением; проверки ошибок и готовности; инструкция использования и фактический первый запуск.

Предполагаемый отдельный каталог — `/opt/veganmedtech`, постоянное имя Compose-проекта — `veganmedtech`. Перед первым изменением проверить занятость каталога, имени проекта и портов. При наличии чужой установки, неизвестного тома или конфликта остановиться без перезаписи. Не менять другие сайты, firewall, sshd, режим парольного входа и пароль root. Не обновлять ОС целиком и не перезагружать сервер.

Если Docker/Compose отсутствуют, допускается установка необходимых пакетов на поддерживаемой Debian/Ubuntu по официальной инструкции Docker после проверки ОС. Уже установленный Docker не переустанавливать. Для иной ОС или конфликтующих пакетов зафиксировать препятствие и уточнить план; не использовать произвольный установщик из сети. Новые Python/JS-зависимости приложению не нужны.

Приватный ключ используется обычным OpenSSH только локально, на сервер передаётся исключительно `.pub`. Новые ключи не создаются. Первоначальный пароль вводится через защищённый интерактивный запрос SSH, без `sshpass -p`, командной строки или записи в файл. Проверка host key сохраняется; при первом доверии записать полученный отпечаток и способ принятия, не подменять проверку настройкой `StrictHostKeyChecking=no`. Если независимой сверки отпечатка нет, явно указать первое доверие, не заявлять проверку через панель хостера.

Локальные `.env*`, `.aws/`, `.codex/`, `.agents/` не читать и не передавать. Серверный файл окружения создаётся отдельно с правами `0600` и новыми случайными секретами только при первом запуске. Повторный деплой не пересоздаёт секреты, не удаляет том БД и не выполняет `down -v` или общую очистку Docker. Единственное исключение редакции 2 — разовая адресная очистка проверенных build-cache ID, созданных единственной сборкой WORK-0012, до первой успешной поставки. Это не очистка образов, контейнеров или томов. Образы current/previous и все копии БД сохраняются. Содержимое серверных секретов не выводится; проверяются полнота настроек и права.

Миграции и замена контейнера могут вызвать короткий перерыв. Обновление выполняется только после успешных переноса и сборки. Перед обновлением существующей БД нужна проверенная копия; при сбое копирования, сборки или создания копии дальнейшие шаги прекращаются. При сбое миграции/readiness скрипт возвращает ошибку и сохраняет предыдущие исходники, образ и копию; автоматический откат схемы БД не выполняется. Документировать конкретные действия восстановления.

Принцип минимализма: сохранить базовые образы, версии/lock, Django/PostgreSQL и Compose; изменить Dockerfile на два этапа только ради удаления инструмента и кэша сборки из runtime. Использовать имеющийся локальный Docker, Bash/OpenSSH и перенос по явному списку файлов. Не добавлять CI/CD, реестр образов, оркестратор, reverse proxy, мониторинг, внешние аккаунты, клинические правила или новые интерфейсы. Автодеплой в этой задаче означает запуск одной командой разработчика, без триггера по Git push.
