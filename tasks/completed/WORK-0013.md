## Запрос и цель

Запрос разработчика 2026-10-25: «нужно сделать так, чтобы к сайту можно было подключиться с других устройств». Уточнение разработчика: «Через интернет к серверу 94.103.3.149».

Результат: с другого компьютера или телефона можно открыть `https://94.103.3.149` без SSH-туннеля и установки собственного корневого сертификата. Браузер сначала запрашивает отдельные реквизиты закрытой демонстрации, затем доступны существующие регистрация и вход в аккаунт приложения. Адрес и инструкция получения реквизитов передаются разработчику после фактической проверки.

Основание — служебное поручение разработчика, продолжение [WORK-0012](WORK-0012.md). Новая продуктовая функция не вводится. Сохраняются CON-001, CON-002, CON-008, CON-010, NFR-003, NFR-008, NFR-013 и FR-010 из [реестра](../../docs/product/requirements.json), серверные права и границы [SPEC-001](../../specs/001-access-and-self-report/spec.md). После аппрува описать AC-001-40 / TEST-001-40 и технический журнал решения в существующем комплекте SPEC-001; историческую закрытую поставку WORK-0012 сохранить.

## Границы и риски

Входит:

- HTTPS по существующему публичному IPv4, автоматическое получение и продление доверенного IP-сертификата; открытые TCP 80/443 для ACME, перенаправления и сайта.
- Один Caddy перед приложением. Приложение и Mailpit сохраняют loopback-порты 18008/18025, PostgreSQL не публикуется. Caddy работает отдельным системным пользователем как systemd-служба и пересылает только запросы сайта.
- Дополнительный пароль закрытой демонстрации на весь HTTPS-сайт, включая статику, с хранением хеша у proxy. Это сохраняет текущую границу материалов опросников из [политики контента](../../docs/clinical/content-policy.md); обычная регистрация приложения сама по себе не закрывает статические тексты опросников. Пароль демонстрации не заменяет проверку аккаунта, роли и связи пациента на сервере.
- Настройки HTTPS, разрешённого Host, CSRF и доверия единственному proxy; стабильность конфигурации и повторной поставки, проверка сохранности и резервной копии.
- Фактическая установка и запуск на указанном сервере через существующий SSH-алиас после аппрува этой редакции.

Не входят домен/DNS, внешний SMTP, новые опросники, клинические правила, изменения интерфейса, публичный доступ к Mailpit, новые роли, производственная эксплуатация и реальные сведения пациентов. Подтверждение email и восстановление пароля по-прежнему используют закрытый Mailpit; оператор получает письма по SSH-туннелю. Ссылки в письмах должны вести на HTTPS-адрес сайта. Пароль демонстрации и серверные секреты не помещаются в исходники, чат или отчёт; разработчику даётся команда их получения по уже настроенному SSH. Локальные `.env*` не читаются и не меняются.

Новый компонент нужен для TLS и ограниченного доступа из интернета. Предпочтительна установка проверенного готового бинарного файла Caddy на хосте: она не добавляет ещё один контейнерный образ на сервер с диском 5 GB. Точную версию и SHA-256 зафиксировать до установки по официальному релизу; не использовать плавающий `latest` и сторонние модули.

Риски: небольшой запас диска, занятые порты, внешний firewall хостера, ошибка ACME/автопродления, цикл HTTPS-перенаправлений, подмена proxy-заголовков и неудачная миграция серверной конфигурации. Сначала проверить предпосылки и синтетическое окружение. Для нового образа сохранить прежнюю консервативную проверку места и резерв; отдельно измерить дополнительные файлы proxy и повторную поставку. Для повтора неизменной версии использовать уже установленный образ только после проверки его содержимого по manifest, без повторной передачи того же образа. Это нужно для проверяемого повтора на текущем диске, не вводит общую систему кэширования. При нехватке места остановиться и зафиксировать фактическое препятствие, не удалять образы/копии/тома автоматически. Нельзя заменять чужие службы, настройки или правила firewall. Разрешены только адресные правила TCP 80/443 для этого сайта с сохранением SSH; внешняя фильтрация хостера требует доступных оператору настроек.

До аппрува разрешены только чтение, проверки существующего состояния и этот файл. Общий запрос и выбор доступа через интернет не считаются аппрувом ещё не рассмотренной редакции.

## План выполнения

1. Зафиксировать явный аппрув редакции 1 и перейти в выполнение. Уточнить SPEC-001: AC-001-40 / TEST-001-40, TASK-001-30–32, трассировку и журнал решений. Создать короткий ADR-0003 для текущего выбора Caddy, IP-сертификата, границы proxy и пароля демонстрации. Не добавлять продуктовое требование ради настройки эксплуатации.
2. Проверить актуальные первичные документы Caddy, Let's Encrypt, Django 5.2 и установленного allauth. Зафиксировать версию/контрольную сумму бинарного файла. Локально проверить конфигурацию Caddy. При серверной установке выполнить выпуск IP-сертификата с явным ACME issuer Let's Encrypt и профилем `shortlived`: сначала staging в отдельном хранилище, затем доверенный сертификат. Самоподписанный сертификат и HTTP-доступ к аккаунтам не являются готовым результатом.
3. В `backend/config/settings.py` добавить явный opt-in доверия HTTPS-заголовку единственного proxy; передать настройку через Compose. В интернет-режиме задать `APP_DEV_MODE=0`, `APP_BASE_URL=https://94.103.3.149`, точный allowed host и доверенный CSRF origin. Caddy перезаписывает `X-Forwarded-Proto` и заголовок IP клиента, сохраняет правильный Host; Basic Authorization после проверки удаляется перед отправкой приложению. Для allauth задать проверенный контракт IP за одним proxy, чтобы клиентская подмена заголовка не обходила ограничения запросов. В локальном режиме доверие proxy остаётся выключенным.
4. Добавить минимальные шаблоны Caddy/systemd: один HTTPS-адрес, перенаправление с HTTP, Basic Auth для всего содержимого сайта, upstream `127.0.0.1:18008`, постоянное закрытое TLS-хранилище и автоматический запуск/перезапуск. Не включать журналирование тел, cookies и Authorization. Административный API Caddy наружу не публиковать. Сгенерировать независимый случайный пароль демонстрации один раз на сервере, сохранить исходные реквизиты в отдельном операторском файле 0600, proxy передать только хеш; повтор не меняет их.
5. Расширить `scripts/deploy.sh` явным режимом `--internet` и включить новые необходимые файлы в allowlist. До изменений проверить владельца установки, свободные порты, место и корректность старой конфигурации. Под блокировкой сохранить закрытую копию старых настроек и БД, проверить `pg_restore --list`, сохранить существующие DJANGO_SECRET_KEY/POSTGRES_PASSWORD и том. Изменять только известные несекретные параметры перехода с закрытого HTTP-демо на HTTPS, без вывода полного env. После локальной сборки установить proxy и применить проверенную конфигурацию приложения. Для неизменного образа сверить переносимый content ID/метку/архитектуру с уже установленным образом и повторно использовать его без транспортного файла; несовпадение возвращает обычный путь полной поставки и прежнюю проверку места. При ошибке остановить публикацию, сохранить прежние артефакты и описать возврат к прежним настройкам; не заявлять автоматический откат схемы. Повторный `--internet` сохраняет режим, реквизиты, сертификаты и данные; обычный закрытый режим не должен молча переключать уже опубликованное окружение назад.
6. Выполнить проверки нового режима/отказов и существующие серверные тесты на выделенной PostgreSQL test database. Проверить обе роли, чужого пациента, CSRF, Secure-cookie, недоверенный Host и подменённые proxy-заголовки. После локальной проверки выполнить первый и повторный интернет-деплой, проверить синтетическую запись и восстановление копии в новую отдельную БД, удалить только созданные проверкой синтетические записи/БД. Рабочий том и существующие аккаунты не сбрасывать.
7. Проверить HTTPS с клиента вне сервера без туннеля и отключения проверки сертификата, всю цепочку сертификата, отсутствие доступа без пароля демонстрации, вход обеих ролей и запись/чтение самоотчёта. Браузерный прогон выполнить при 390 и 1440 px; сохранить матрицу и границы фактической проверки устройств. Проверить restart службы и повторное использование TLS-хранилища. В отдельном staging-хранилище поддерживаемым параметром настроить тестовое окно продления и проверить получение нового сертификата по serial/событиям ACME; рабочий сертификат не заменять, реальное продление production-сертификата этим не заявлять.
8. Самостоятельно проверить каждый CHECK и записать реальные команды, результаты и локальные свидетельства в отчёт внутри этой задачи. Обновить README, SPEC-001 и PROJECT_STATUS.md по факту, проверить TECH_DEBT.md и сразу фиксировать обнаруженный долг. После успешной самопроверки перенести полную задачу в `tasks/completed/WORK-0013.md`, вернуть CURRENT_TASK.md в `idle` и повторить структурную проверку и unit-тесты.
